# Установка Камертона

[English version](install.md)

| Что хотите сделать | Куда дальше | Готово, когда |
|---|---|---|
| Попробовать на этом компьютере без DNS | [Локально](#локально-без-dns) | Открывается `http://localhost:8091` |
| Уже есть Nginx Proxy Manager (NPM) или другой HTTPS-прокси | [Готовый HTTPS-прокси](#готовый-https-прокси) | По HTTPS открывается вход владельца; Caddy не запущен |
| HTTPS-прокси нет, TCP-порты 80 и 443 свободны | [Caddy](#caddy) | Caddy отвечает по HTTPS, владелец может войти |

Нужны Git, Python 3.10+ и локальный Docker для Linux-контейнеров с Compose 2.24.4+. Используйте Docker Engine 28+: [более ранние версии могли открывать loopback-порты в локальную сеть](https://docs.docker.com/engine/network/port-publishing/).

**Windows с Docker Desktop:** откройте терминал Ubuntu в WSL 2, а не PowerShell. В Docker Desktop включите бэкенд WSL 2 и интеграцию для Ubuntu: **Settings → Resources → WSL Integration**. В Ubuntu выполните `cd ~` перед клонированием. Держите репозиторий и каталог `--root` в файловой системе Linux, не в `/mnt/c`: базе владельца и закрытым файлам нужны права Linux.

В Bash клонируйте версию с файлом `scripts/kamerton.py`: `git clone https://github.com/mazixs/stt-api.git && cd stt-api`.

**Камертон уже работает?** Начните с [переноса](#перенос-существующего-стека), а не с `init` или `setup`. По умолчанию CLI пишет в каталог репозитория. Для установки в отдельный пустой каталог указывайте `--root` перед подкомандой при каждом вызове. Не выполняйте прямой `docker compose up` над каталогами установки CLI: он запустит отдельный проект.

## Локально, без DNS

```bash
python3 scripts/kamerton.py setup local
```

Откройте `http://localhost:8091` на компьютере, где работают браузер и Docker. Оставьте привязку к loopback: входа владельца здесь нет, режим не предназначен для публикации в сети. Если нужен другой `HOST_PORT` или локальный `API_KEY`, **вместо** `setup local` выполните `python3 scripts/kamerton.py init local`, измените `.env`, затем выполните `python3 scripts/kamerton.py start`. Один ключ даёт доступ и к распознаванию, и к управлению консолью. Перейдите к [первому распознаванию](#первое-распознавание).

## Готовый HTTPS-прокси

**Браузер или клиент → HTTPS (ваш прокси) → HTTP (Камертон на 8812).** Разрешите доступ к опубликованному порту только прокси и не перенаправляйте порт из интернета. Привязка к интерфейсу не ограничивает источник: задайте правило в сетевом файрволе или в правилах хоста для опубликованных портов Docker. Caddy не запускайте. Выберите домен и сертификат по разделу [«DNS и сертификаты»](#dns-и-сертификаты).

1. Выполните `python3 scripts/kamerton.py init npm`. Заполните `.env.npm` по [образцу](../.env.npm.example):
   - `KAMERTON_BIND` — конкретный IPv4 интерфейса сервера Камертона, доступного с прокси, не `0.0.0.0`. `KAMERTON_PORT` по умолчанию `8812`.
   - `PUBLIC_ORIGIN` — адрес в браузере, например `https://stt.example.org`. Замените имя своим; не дописывайте путь, `/` на конце или `:443`.
   - `TRUSTED_PROXY_IP` — **один IP непосредственного соединения, который видит Камертон**. Это не подсеть, не IP клиента и не значение `X-Forwarded-For`. Из-за Docker или NAT адрес может отличаться от адреса прокси. Проверьте фактический маршрут и закрепите адрес, доступный только прокси. Не доверяйте общему шлюзу, если через него к бэкенду может прийти другой трафик с тем же IP.
2. Выполните `python3 scripts/kamerton.py owner create` и ответьте на вопросы, затем запустите `python3 scripts/kamerton.py start`. Первый владелец создаётся на сервере, а не на сайте. Сохраните логин и пароль в менеджере паролей.
3. В NPM добавьте **Proxy Host**. В **Domain Names** укажите имя из `PUBLIC_ORIGIN`, в **Scheme** — `http`, в **Forward Hostname / IP** — адрес бэкенда, доступный *из NPM* (обычно `KAMERTON_BIND`), а не домен сайта, в **Forward Port** — `8812` или заданное вами значение. В разделе **SSL** выдайте или выберите сертификат для имени сайта и включите **Force SSL**. `localhost` из NPM не указывает на бэкенд в другом контейнере или на другом компьютере.
4. В официальном Nginx Proxy Manager вставьте [блок `location /` целиком](../deploy/npm-location.conf) на вкладке **Advanced** у Proxy Host, не в **Custom Locations**. Блок заменяет штатный `location`: если используете Access List, не считайте, что ограничения сохранились. В NPMplus и других прокси не копируйте этот блок вслепую: проверьте, что правило передаёт один `Host` с внешним именем и портом и `X-Forwarded-Proto: https` для TLS, а `X-Kamerton-Client-IP` **перезаписывает** по IP, который видит сам прокси, или удаляет, если IP неизвестен. Не пропускайте значение клиента. Сохраняйте `Origin`, cookie и `Authorization`. Оставьте запас над `MAX_UPLOAD_MB` на multipart и отключите буферизацию ответа для потока событий.

**Готово, когда:** по HTTPS открывается `/login`, владелец может войти, а `GET /v1/models` без ключа через HTTPS возвращает `401`. Прямой запрос к бэкенду с другого компьютера должен блокироваться или отклоняться. Перейдите к первому распознаванию.

## Caddy

**Браузер или клиент → HTTPS (Caddy) → HTTP (Камертон во внутренней сети Docker).** Только Caddy занимает порты 80 и 443 на хосте. Не запускайте этот профиль рядом с прокси, который уже слушает эти порты.

1. Выполните `python3 scripts/kamerton.py init caddy`. В `.env.public` задайте `KAMERTON_DOMAIN` — доменное имя без схемы, порта и пути. В [образце](../.env.public.example) есть `CADDY_BIND` и настройки сети Docker; если подсеть пересекается с уже существующей сетью, меняйте подсеть и оба IP вместе.
2. Направьте DNS на Caddy и настройте получение сертификата по разделу ниже. Выполните `python3 scripts/kamerton.py owner create`, затем `python3 scripts/kamerton.py start`.
3. Откройте сайт по HTTPS и войдите с учётными данными владельца. Подробности — в [справочнике по ручному запуску Caddy](public-access.md).

**Готово, когда:** браузер доверяет сертификату, владелец входит, HTTP-порт Камертона не опубликован на хосте. Теперь попробуйте распознавание.

## Первое распознавание

1. В разделе **«Модели»** выберите **GigaAM v3 RNN-T end-to-end** (`e2e_rnnt`), откройте **«Настройки запуска»** и нажмите **«Развернуть»**. Дождитесь готовности. При первом развёртывании скачивается около 230 МБ весов.
2. В **«Диктовке»** загрузите короткий WAV с речью или запишите фразу и остановите запись. Должен появиться текст. Разрешите браузеру доступ к микрофону. Запись работает по `http://localhost` на компьютере с браузером либо по HTTPS с доверенным сертификатом. На телефоне `localhost` — сам телефон, не сервер Docker; обычного HTTP по LAN-адресу недостаточно. Загрузить файл можно без доступа к микрофону.
3. Для подключения приложения по HTTPS откройте **«API-ключи клиентов»**, укажите название и нажмите **«Создать ключ»**. Сразу скопируйте ключ: он показывается один раз. Base URL — `https://stt.example.org/v1` с вашим доменом, модель — `kamerton`, ключ передаётся как `Authorization: Bearer …`. Ключ можно отозвать отдельно; управлять консолью он не позволяет. Для локального режима Base URL — `http://localhost:8091/v1`; используйте `API_KEY` из `.env`, если он задан. Иначе ключ не нужен; если клиент не даёт оставить поле пустым, введите любое непустое значение.

Чтобы проверить HTTPS API, положите `recording.wav` в текущий каталог. При вводе ключ не отображается:

```bash
read -r -p 'Base URL (включая /v1): ' base_url
read -r -s -p 'Ключ клиента: ' STT_API_KEY; printf '\n'
curl --fail-with-body "${base_url%/}/audio/transcriptions" \
  --header "Authorization: Bearer $STT_API_KEY" \
  --form-string 'model=kamerton' --form 'file=@recording.wav'
unset STT_API_KEY
```

**Готово, когда:** консоль или клиент возвращает текст вашей записи. `kamerton` — постоянный ID API. Рабочая модель меняется в консоли, а не в настройках клиента.

## DNS и сертификаты

- **Только LAN или VPN.** Во внутреннем DNS направьте имя на доступный адрес TLS-прокси. При split DNS одно и то же имя указывает внутри сети на LAN-адрес, снаружи — на публичный адрес прокси. Имя в браузере, сертификате и `PUBLIC_ORIGIN` должно совпадать.
- **Доступ из интернета.** Публичная `A`-запись указывает на доступный IPv4 прокси. Добавляйте `AAAA`, только если по IPv6 тоже можно подключиться: профиль Caddy по умолчанию привязан к IPv4. На роутере или в файрволе пропускайте трафик к TLS-прокси, а не к бэкенду Камертона. Для обычной проверки ACME должен быть доступен порт 80 (HTTP-01) или 443 (TLS-ALPN-01) в зависимости от способа проверки.
- **LAN без открытых входящих портов.** Нужен сертификат, которому доверяют ваши устройства. Если прокси поддерживает DNS-01, публичный центр сертификации может подтвердить DNS-имя без доступа к сайту из интернета. Другой вариант — установить публичный корневой сертификат своего CA на каждом устройстве. Если нужен именно внутренний CA Caddy, выберите [ручную настройку Caddy](public-access.md#частые-вопросы) **вместо** установки Caddy через CLI: команды справочника не управляют проектом CLI. Проверьте DNS, доверие к сертификату и микрофон на устройстве, с которого будете пользоваться Камертоном.

## Остановка, повторная установка, резерв и откат

- `python3 scripts/kamerton.py stop` останавливает установку, `start` запускает её снова. Кнопка **«Остановить»** в консоли останавливает только движок. Для диагностики используйте команды `status`, `doctor`, `logs --follow` того же CLI.
- При повторной установке на том же Docker Engine и по тому же абсолютному пути сохраните `.kamerton/`, env-файл профиля, `data/`, `models/` и тома Caddy, если он используется. Сохраните прежнее хранилище владельца. Если забыли пароль, используйте `owner reset-password`. Другой путь, Docker Engine или профиль требует [переноса с остановкой](#перенос-существующего-стека), а не повторной инициализации рабочих данных.
- `python3 scripts/kamerton.py backup` останавливает сервисы на время копирования и запускает их обратно, если они работали. Команда выводит путь копии в `.kamerton/backups/`: в ней лежат конфигурация и `data.tar` с данными владельца, настройками и томами Caddy. Вынесите копию за пределы установки и храните её закрыто. Модели, образы, настройки внешнего прокси и его сертификаты при необходимости сохраните отдельно.
- Для работающего стека выполните `git fetch --tags` и `python3 scripts/kamerton.py update --version v1.6.0`, подставив нужный совместимый тег. Для уже доступного локального образа есть `update --image`. CLI делает резерв перед заменой приложения и при сбое пытается вернуть предыдущий образ. Для отката на совместимую версию укажите прежний тег или образ. Ни смена версии, ни `recover` не восстанавливают БД из резерва. Если релиз сменил формат данных, остановите все сервисы, которые используют эти файлы, и проверьте старый образ с подходящим резервом отдельно, прежде чем восстанавливать данные в исходном каталоге. `recover` завершает прерванную операцию CLI, а не восстанавливает произвольный архив.

## Arcane GitOps

Укажите путь к файлу Compose относительно корня репозитория. Для готового прокси выбирайте **`docker-compose.npm.yml`** — это самостоятельный файл. **`docker-compose.yml`** сам по себе запускает локальный профиль. **Не выбирайте один `docker-compose.public.yml`**: это наложение Caddy, которому нужен базовый файл. Запускайте Caddy через CLI из рабочей копии, если в вашем способе развёртывания нельзя передать Compose оба файла.

- **Проверьте исходники для сборки.** [Git Sync](https://getarcane.app/docs/docker/git-sync) может копировать в проект Arcane только YAML. Для NPM предоставьте полный контекст сборки нужной версии, включая `Dockerfile`, `console/` и зависимости, либо задайте `KAMERTON_BUILD_CONTEXT` как Git-контекст с тегом релиза или полным SHA коммита. У сборщика должен быть доступ к этому репозиторию. Arcane может сохранить Compose под другим именем — не рассчитывайте на исходное имя в каталоге проекта.
- **Задайте окружение проекта в Arcane.** В режиме одного YAML перенесите значения из [`.env.npm.example`](../.env.npm.example) в окружение GitOps: `.env.npm` автоматически не читается. Для `KAMERTON_DATA_DIR` и `KAMERTON_MODEL_DIR` используйте абсолютные пути на Docker-хосте. Не направляйте `COMPOSE_FILE` и `COMPOSE_ENV_FILES` на отсутствующие файлы из Git.
- **Соберите и проверьте нужный образ.** Укажите в `KAMERTON_IMAGE` отдельный локальный тег для версии, а в `KAMERTON_BUILD_CONTEXT` закрепите соответствующие исходники. Если локальный образ уже есть, смена контекста и Git Sync не гарантируют пересборку. При сомнении соберите образ явно, как ниже, и проверьте, что Arcane использует тот же тег.
- **Выключенный Auto Sync — не блокировка.** Нет загрузки по расписанию, но ручной **Sync from Git** может заменить YAML и переразвернуть работающий стек. Сначала проверьте переход в отдельном проекте, на других портах и с другими каталогами данных и моделей.

На Docker-хосте работайте из фактического каталога проекта Arcane. Используйте [скрипт для Arcane](../scripts/arcane.sh): ему нужны Bash и Python 3 без дополнительных пакетов. Если клонировали репозиторий в другую папку, подставьте её путь в команды ниже. Каждая команда спросит локальный контекст Docker, имя проекта Compose, путь к его YAML и закрытому env-файлу с теми же значениями, что в Arcane. При заданном `DOCKER_HOST` или удалённом контексте скрипт остановится, а не переключится на другой Docker Engine.

```bash
bash "$HOME/stt-api/scripts/arcane.sh" check
bash "$HOME/stt-api/scripts/arcane.sh" build
```

`check` ничего не меняет: сравните ID Docker Engine, пути монтирования, порт и origin с рабочими настройками Arcane. `build` просит подтверждение и собирает образ без запуска веб-сервиса. **Для существующего стека** проверьте наличие исходных каталогов и `owner.sqlite3`. Не создавайте пустую замену и не выполняйте `init`.

**Только для нового стека** создайте два проверенных каталога на Docker-хосте (`mkdir -p` с их абсолютными путями) и выполните `bash "$HOME/stt-api/scripts/arcane.sh" create-owner`. Скрипт запросит пароль без отображения и запишет его хеш только в пустой каталог данных, где нет даже скрытых файлов. Он не переведёт остановленную локальную установку в режим владельца. Веб-сервис запускайте **в Arcane**, не через установщик.

## Перенос существующего стека

Установщик не импортирует существующие стеки Compose и не переключает профиль установки. Не меняйте способ управления рабочим стеком, пока отдельно готовите и проверяете новый.

1. **Сверьте рабочую установку до изменений.** Запишите имя проекта, Compose, образ или Git-ревизию, фактические значения переменных, исходные пути монтирования `data/` и `models/`, порты, сеть, доверенный peer, домен, сертификат и настройки прокси. Сопоставьте с целевым профилем. Например, для NPM укажите внешний origin в `PUBLIC_ORIGIN`, а `TRUSTED_PROXY_IP` определите заново для нового маршрута от прокси к бэкенду. Не рассчитывайте, что относительные пути Arcane укажут на прежние каталоги.
2. **Снимите резерв.** Приостановите автоматические выкладки и остановите прежний стек на время копирования. Сохраните фактический `data/`, конфигурацию развёртывания и TLS-материалы, которыми управляете. Оставьте доступ к старой версии и настройкам для отката. Проверьте итоговую конфигурацию нового стека без вывода секретов. Отдельно проверьте переход с **копиями** данных, другими портом и сетью и подходящим тестовым origin. Пока не запускайте ручной Sync рабочего проекта.
3. **Переключайте по одному экземпляру.** Остановите старый сервис до запуска нового на исходных данных. Не запускайте два процесса на одном `data/`. Существующий `owner.sqlite3` используйте как есть: не выполняйте `init` и не создавайте владельца заново. После переключения проверьте по HTTPS вход, микрофон и распознавание из приложения. Для отката остановите новый стек, верните прежнюю конфигурацию и при необходимости подходящие данные, запустите только прежний стек и направьте прокси обратно на него.

## Если что-то не работает

| Симптом | Что проверить сначала |
|---|---|
| `502 Bad Gateway` | Запущен ли Камертон? Проверьте из сети прокси адрес бэкенда, схему HTTP, порт, привязку и файрвол. Если сам Камертон вернул `503`, движок ещё не готов; откройте **«Статус сервиса»**. |
| `403` по HTTPS | Сверьте IP непосредственного соединения, точный внешний `Host` и единственный заголовок `X-Forwarded-Proto: https`. Если не проходит только действие в браузере, проверьте origin и войдите заново. Не обходите проверки. Ответ `401` от `/v1/models` при подключении клиента означает, что ключ отсутствует, неверен или отозван. |
| Порт занят | До первого успешного запуска через CLI выберите свободный `HOST_PORT` (локально) или `KAMERTON_PORT` (NPM) и обновите Forward Port у прокси. После первого запуска CLI не принимает смену порта: освободите порт или перенесите стек. Если 80/443 уже заняты HTTPS-прокси, используйте его вместо Caddy. |
| Предупреждение о сертификате или нет микрофона | Проверьте DNS с клиентского устройства, имя и цепочку доверия сертификата, затем разрешение сайта на микрофон. При проблемах с выдачей проверьте устаревшие `AAAA` и доступность проверки ACME. Не игнорируйте предупреждения браузера о сертификате. |
