# Камертон по HTTPS: владелец и ключи приложений

Локальный `docker-compose.yml` оставляет консоль на `127.0.0.1:8091`. Для телефона, ноутбука или отдельного API-клиента можно включить [наложение с Caddy](../docker-compose.public.yml). В нём у веб-контейнера **нет порта на хосте**, даже на loopback. Владелец входит в браузере по логину и паролю. Приложение получает отдельный ключ, который можно отозвать без смены пароля и перезапуска модели.

## Включить

Нужен Docker с Compose **2.24.4 или новее** (не `docker-compose` v1): наложение сбрасывает публикацию портов и унаследованный `env_file`. Команды ниже — для Bash в каталоге установки. Если переносите существующий экземпляр, остановите его прежней командой `down` **без `-v`**, сохраните копию `data/` и не запускайте два процесса на одном каталоге. Для чистой установки этот шаг не нужен.

1. Скопируйте `.env.public.example` в `.env.public`. Укажите в `KAMERTON_DOMAIN` своё DNS-имя **без** схемы, порта и пути. `CADDY_BIND` определяет доступные интерфейсы: по умолчанию все IPv4, для VPN — адрес интерфейса VPN. Если подсеть пересекается с Docker, LAN или VPN, поменяйте `KAMERTON_SUBNET`, `KAMERTON_CADDY_IP` и `KAMERTON_APP_IP` вместе. При переносе вручную перенесите нужные значения `MAX_UPLOAD_MB`, `AUTOSTART`, `ENABLE_MODEL_COMPARE`, `LOG_LEVEL` и `HF_TOKEN` в `.env.public`. Старый `.env` не загружается: без переноса, например, лимит снова будет 150 МиБ. `API_KEY` и пароль владельца в `.env.public` не копируйте; параметры уже развёрнутой модели остаются в `data/state.json`.
2. Проверьте конфигурацию и соберите образы. Используйте одну и ту же команду `public` для всех операций с профилем. Для обычной установки с публично доверенным сертификатом DNS-имя должно указывать на Caddy, а проверка домена должна проходить на TCP 80 или 443. Если опубликована AAAA-запись, за ней тоже должен быть доступный Caddy. Для изолированной сети см. FAQ ниже.

```bash
public() { docker compose --env-file .env.public -f docker-compose.yml -f docker-compose.public.yml "$@"; }
public config -q
public build --pull --no-cache stt-api caddy
```

3. Создайте владельца **до** запуска веб-сервиса. Этот пример спрашивает пароль без эха и монтирует временный файл только в одноразовый CLI. Файл создаётся вне проекта; ни сборка, ни работающий сайт, ни Caddy не получают пароль. Замените `owner` своим логином и сохраните его для восстановления.

```bash
owner() (
  set -eu
  umask 077
  password_file=$(mktemp /tmp/kamerton-owner.XXXXXXXX)
  trap 'rm -f "$password_file"' EXIT
  IFS= read -rs -p 'Пароль владельца: ' password; printf '\n'
  printf '%s' "$password" > "$password_file"; unset password
  public --profile setup run --rm --no-deps \
    -e ADMIN_USERNAME=owner -e ADMIN_PASSWORD_FILE=/run/secrets/owner-password \
    -v "$password_file:/run/secrets/owner-password:ro" owner-cli "$@"
)
owner init
```

**Если есть старые клиенты**, выберите способ миграции *вместо* последней команды: сохраните прежний `API_KEY` в закрытом `.env.owner` с правами `0600` и выполните `owner init --import-legacy`. Для ключа с `$` или другими специальными символами используйте одинарные кавычки в `.env.owner`: например, `API_KEY='literal$part'`, чтобы Compose не подставил переменную. Ключ станет отзывным ключом `legacy`, но не паролем владельца. Обычный `owner init` не импортирует его. Повторный `init` не заменяет существующую БД. После успешной операции уберите `.env.owner`; простой перезапуск не импортирует ключ заново.

Альтернатива файлу пароля: указать `ADMIN_USERNAME` и `ADMIN_PASSWORD` в закрытом `.env.owner`, затем выполнить `public --profile setup run --rm --no-deps owner-cli init` без функции `owner`. CLI требует **ровно один** источник пароля. Не задавайте оба, даже если один пуст. `.env.owner` читает только CLI; пароль в переменной виден администратору Docker до удаления контейнера. Не печатайте `docker compose config` с секретами — для проверки достаточно `config -q`.

4. Запустите сайт и войдите на **`https://ваш-домен`**. Кнопки первичной регистрации и сетевого сброса нет. Для смены пароля выполните `owner reset-password` с тем же логином и новым паролем; существующие сессии перестанут действовать.

```bash
public up -d --wait
public ps
```

## Подключить приложение

Войдите в консоль, создайте именованный ключ клиента и сразу сохраните его в приложении: повторно показать значение нельзя. Base URL клиента — `https://ваш-домен/v1`. Используйте `Authorization: Bearer <ключ>` для списка моделей и распознавания; `audio/translations` отвечает, что перевод не поддерживается. Ключ не даёт доступ к настройкам, журналу, схеме OpenAPI или произвольным маршрутам движка. Сессия браузера и ключ приложения не взаимозаменяемы. Не передавайте ключ в URL.

## Проверить границу доступа

```bash
docker inspect "$(public ps -q stt-api)" --format '{{json .HostConfig.PortBindings}}'
docker inspect "$(public ps -q caddy)" --format '{{json .HostConfig.PortBindings}}'
public exec -T stt-api curl -fsS http://127.0.0.1:8080/health
curl -sS -o /dev/null -w '%{http_code}\n' https://ваш-домен/health
```

У `stt-api` ожидается `{}`, у Caddy — TCP 80 и 443. Внутренний healthcheck получает `200`, внешний — `404`. Если на этом хосте уже работает другая локальная установка, ответ на `localhost:8091` может прийти от неё: проверяйте именно `PortBindings` нужного контейнера.

На выделенном bridge только `caddy` и `stt-api`; upstream — `stt-api:8080`, движок — `127.0.0.1:9876` внутри `stt-api`. Обычный bridge сохраняет маршрут наружу для загрузки весов. Порты приложения и движка не публикуются. Uvicorn передаёт приложению реальный IP непосредственного соединения; доверенным считается только адрес Caddy. Доверие не распространяется на всю подсеть или произвольные forwarded-заголовки. CLI работает без сети. Журнал HTTP-запросов выключен; Caddy не пишет URL и заголовки даже при ошибке upstream.

## Частые вопросы

**Как пользоваться одним адресом в LAN и снаружи?** Сделайте внутреннюю запись DNS для того же имени на LAN-адрес Caddy, внешнюю — на внешний адрес. Тогда сертификат и `PUBLIC_ORIGIN` совпадают в обеих сетях. Пример в UI меняет адрес для подключения клиента, а не настройки DNS или порт сервера.

**Нужен ли доступ из интернета только ради микрофона?** Нет. Оставьте доступ через VPN или LAN, но используйте HTTPS с сертификатом, которому доверяет устройство. `http://localhost` — исключение только на том устройстве, где открыт браузер. Для закрытого DNS можно использовать частный CA Caddy: добавьте `tls internal` в блок домена [Caddyfile](../Caddyfile), пересоздайте Caddy и экспортируйте **только публичный корень** командой `public cp caddy:/data/caddy/pki/authorities/local/root.crt ./root.crt`. Чтобы телефон и ноутбук доверяли сайту, настройте на них доверие к этому корню. Закрытый ключ CA остаётся в томе. Если системное доверие менять нельзя, используйте сертификат уже доверенного CA. Сертификат, разрешение на микрофон и запись нужно проверить на каждом устройстве.

**Что перенести на другой сервер?** Остановите профиль (`public down`, без `-v`). Перенесите `data/` целиком, включая `owner.sqlite3`, `models/`, `.env.public`, `Caddyfile` и содержимое именованных томов `caddy_data` и `caddy_config`. Копии БД и `/data` Caddy храните как секреты. При смене имени Compose-проекта изменятся и имена томов: восстановите их содержимое до `up`. Проверьте права на файлы и отсутствие конфликта подсети, перенаправьте DNS. Если домен изменился, обновите `KAMERTON_DOMAIN`, войдите заново и измените Base URL клиентов. Пароль владельца по сети переносить не требуется.

**Как вернуться к локальному режиму без потери данных?** Сначала отключите старую внешнюю маршрутизацию (в том числе прокси на хосте или туннель) и выполните `public down` **без `-v`**. Команда `public ps -a -q caddy` не должна вывести ID. Не запускайте локальный профиль за оставшимся публичным Caddy. В локальном `.env` установите `HOST_BIND=127.0.0.1`, непустой **новый** `API_KEY` и `ALLOW_OWNER_LOCAL_ROLLBACK=1`; не включайте `OWNER_ACCESS`. Без этого подтверждения запуск локального режима поверх БД владельца блокируется. Базовый режим не учитывает отзыв старого ключа в БД.

Перед `up` проверьте итоговую конфигурацию, не печатая её секреты. Эта команда требует Python 3 на хосте и запускает локальный профиль, только если есть один сервис, порт привязан к loopback и ключ задан:

```bash
local_stack() { docker compose --env-file .env -f docker-compose.yml "$@"; }
local_stack config --format json | python3 -c '
import json, sys
s = json.load(sys.stdin)["services"]
web = s["stt-api"]; env = web["environment"]; ports = web["ports"]
ok = (set(s) == {"stt-api"} and len(ports) == 1 and ports[0].get("host_ip") == "127.0.0.1"
      and bool(env.get("API_KEY", "").strip()) and env.get("OWNER_ACCESS", "0") in ("0", "false")
      and env.get("ALLOW_OWNER_LOCAL_ROLLBACK") == "1")
sys.exit(0 if ok else "Проверьте профиль, loopback и переменные отката.")' &&
  local_stack up -d --build --wait
```

Проверьте, что `/api/status` без ключа возвращает `401` и порт привязан только к loopback. БД владельца, глоссарий, модели и сертификаты сохранятся; чтобы вновь включить профиль, остановите локальный сервис (`local_stack down`), пересоберите оба образа (`public build --pull --no-cache stt-api caddy`), затем выполните `public up -d --wait` без повторного `init`.

**Как воспроизвести проверку без публикации сервиса?** Используйте отдельный Compose-проект, образ, временные `data/` и `models/` (также у CLI), отдельную подсеть и тома. В тестовом наложении замените `caddy.ports` на `!override ["127.0.0.1::443"]`, отключите рестарты и `AUTOSTART`, не скачивайте образы и модели. `KAMERTON_DOMAIN=kamerton.localhost` выбирает локальный CA без внешнего ACME. После `public port caddy 443` задайте тестовому приложению `PUBLIC_ORIGIN=https://kamerton.localhost:<выданный порт>` и пересоздайте только `stt-api`. Скопируйте `root.crt` во временный каталог и передайте его конкретному клиенту (`curl --cacert ... --resolve kamerton.localhost:<порт>:127.0.0.1`), не добавляя CA в системное доверие. На приёмочном стенде так проверены TLS, `404` для внешнего `/health`, отсутствие порта веб-контейнера и `421` при несовпадении Host с TLS-именем. Публичный DNS и выдача публичного сертификата для такой проверки не требуются.
